## Open question this plan can't resolve alone

The app now has two distinct GHG calculation models: the original corporate-level scope1/2/3 calculator (`EmissionCalculator.tsx`, the app's current core feature, built on `emission_records`: scope/activity/quantity/factor), and the new facility-level source-stream/calculation-tier model (the 12 MRV tables, built for EAD-grade granularity). Neither session's records say how these relate going forward.

Two real options:

1. **Side by side.** The simple calculator stays the fast, corporate-total tool for users who just need a GHG Protocol number. The MRV layer is a separate, deeper facility-audit workflow for users (or the same user, in a different mode) who need EAD-grade detail. Nothing about the simple calculator changes.
2. **MRV-primary.** Where a facility has MRV source-stream data for a reporting boundary, the simple calculator's totals get derived from that data instead of separately entered scope/activity rows. This is a bigger, more invasive change, it would mean rethinking what `/api/calculate` and `ResultsView.tsx` actually read from.

This plan proposes option 1 below, side by side, because it's non-breaking and matches the schema's own header comment ("framework-agnostic... sitting alongside, not replacing"). But this is a real product decision, not something to assume silently. Needs your call before the navigation structure below gets built.

## Proposed information architecture

The current flat single-page layout won't hold 12 new entity types plus the existing 3. Proposed structure, built from the already-installed `sidebar` component (currently unused):

- **Setup** -- existing `SetupPanel` wizard, unchanged (reporting entity -> facility -> reporting boundary).
- **Facilities** -- list of facilities under the org. Selecting one opens a facility profile screen with three tabs: Identifiers, Contacts, Products (three separate entities today, one screen for the user, matching how EAD's own template groups them under "Facility Description"). Mitigation Measures lives here too, facility-scoped, not boundary-scoped.
- **Reporting Boundaries** (nested under a facility, or listed with a facility+year picker) -- selecting a boundary opens the boundary workspace:
  - **Source Streams** tab -- the core worklist. A table (reusing `table.tsx`) of source streams for this boundary: name, materiality badge, quantification approach, calculated emissions, data-quality tier. Clicking a row opens the source stream detail.
  - **Methane Report** tab -- one form, 1:1 per facility+boundary.
  - **Verification Findings** tab -- list, addable.
  - **Management QA** tab -- list, addable.
- **Calculator** -- the existing scope1/2/3 tool, unchanged, kept as its own nav item (per option 1 above).
- **Team** -- existing `TeamPanel`, unchanged.
- **Audit View** -- new, described below.

## Proposed data-entry flow (first-time, no training)

The biggest first-time-user risk in the current schema is the source stream's three mutually exclusive approaches (calculation-based / measurement-based / fallback). Showing all three forms at once would confuse anyone. Proposed flow per source stream:

1. User creates a source stream with a name and description (required fields only, everything else deferred).
2. A single required choice, presented as three cards or a segmented control, not a dropdown: "How is this measured?" with one-line plain-language descriptions under each (e.g. "Calculation-based: activity data x an emission factor" / "Measurement-based: continuous monitoring equipment" / "Fallback: neither is available, estimate and justify"). This directly maps to which one of the three 1:1 tables gets a row, so the choice has to be made before the detail form renders, not changeable casually afterward (changing it means abandoning the previous approach's data, which should require a confirmation dialog, not a silent switch).
3. Only the chosen approach's form renders. Fields use plain labels with an info tooltip (the `tooltip.tsx`/`hover-card.tsx` components are already installed) explaining EAD/ISO jargon inline ("oxidation factor", "data quality tier") rather than assuming the user already knows it.
4. A Data Quality section always follows, regardless of approach chosen (uncertainty percent, and a required flag + justification if an IPCC default factor was used instead of a more specific one, per this project's own sourcing-hierarchy rule).
5. Materiality (major/minor) is asked once, up front, on the source stream itself, since it affects how prominently it appears in the Audit View later.

## Proposed Audit View

A read-only screen, per reporting boundary, structured the way an audit actually proceeds, not the way data entry proceeds:

- Header: facility identifiers, reporting year, consolidation approach.
- A source-stream table, sortable/filterable by materiality and by verification status, each row expandable (accordion) to show its calculation approach detail, data quality record, and any linked verification findings without navigating away.
- A Methane Report section, a Management QA section, and a Verification Findings list, each visible without drilling into individual streams.
- Nothing editable on this screen. Editing happens only in the entry flow above, this view exists so an auditor (or TeeKay preparing for one) never has to guess where something lives.

## Proposed export design

Two distinct outputs, not one:

1. **Excel export with live formulas** (always available, not conditional). This needs a library that can write formula cells, not just values, `exceljs` or the formula-capable path of `xlsx` (SheetJS) both support this; the current codebase doesn't have either installed yet, worth confirming which one before building. For a calculation-based source stream, the exported sheet should have activity data, emission factor, and oxidation factor as separate cells, with the calculated emissions cell holding an actual formula referencing them (e.g. `=B2*C2*D2`), not a static number copied from the database, so an auditor can open the file and verify the arithmetic themselves, not just trust the displayed total.
2. **EAD-template-shaped export** (only surfaced when an "upload to EAD portal" option is selected, per your instruction). Flagging two real gaps here rather than assuming this is close to done: first, the schema's field structure was informed by the EAD workbook's *structure* (14 sheets, column headers), not verified clause-by-clause against EAD's Technical Guidance document, per the caveat already in `shared/schema.ts`'s own header comment. Building an export that matches the template's exact sheet/column layout needs a fresh pass reading the actual EAD workbook cell-by-cell, not reusing the earlier structural read. Second, and separately, "upload to EAD portal" implies EAD has a submission API or portal upload mechanism, nothing in this codebase or either session's research confirms that exists or what it requires. That's a distinct, unresearched integration question, not something this plan can size until it's looked into.

## Proposed build order

1. Facility profile screen (Identifiers/Contacts/Products tabs) -- lowest risk, no cross-entity dependencies.
2. Source stream list + creation flow, including the three-way approach picker and Data Quality section -- the core of the new work.
3. Boundary-level tabs: Methane Report, Verification Findings, Management QA.
4. Mitigation Measures (facility-scoped).
5. Audit View, once enough real data exists to be worth reviewing.

## Decisions made (2026-08-03, same day, after review)

TeeKay reviewed this plan and made the following calls, superseding the open items above:

1. **Side-by-side confirmed**, and clarified further: scope 1/2/3 is the universal, most granular activity-level taxonomy. ISO 14064-1, EAD, and any other framework are reclassification/reporting layers on the same underlying scope-tagged data, not separate data models. This matches this project's own standing instruction ("All six frameworks share Scopes 1/2/3 quantification as the base layer... do not fork scope-quantification logic per framework").

   Correction on the standards figure that came up in that discussion: ISO 14064-1:2018 defines **six** categories, not four (direct emissions; imported energy; transportation; products used by the org; products supplied by the org; other indirect sources). GHG Protocol's Scope 3 does have 15 categories, confirmed correct. Sources: [ANSI Blog, ISO 14064-1:2018](https://blog.ansi.org/ansi/iso-14064-1-2018-greenhouse-gas-emissions/), [ISO 14064-1:2018 standard page](https://www.iso.org/standard/66453.html), [Novisto, 15 Scope 3 Categories](https://novisto.com/knowledge-base/scope-3-categories-what-are-they).

2. **Concrete schema gap found and confirmed for a new migration**: `source_streams` currently has no `scope` (1/2/3) field and no Scope 3 subcategory (1-15) field, only a free-text `ghg_source_category` column. Migration-003 will add `scope` (enum: scope1/scope2/scope3) and `scope3_category` (integer 1-15, nullable, only meaningful when scope = scope3) to `source_streams`. This is the base taxonomy everything else classifies from, so it has to exist before the classification/selector logic below can work.

   Related gap surfaced by the same review: the two global reference tables seeded in migration-002 (`primary_activity_types`, `product_benchmarks`) have no foreign key anywhere pointing to them. `facility_products.product_category` is free text, not a reference to `product_benchmarks`. Worth deciding whether to wire that up in the same migration pass or separately, flagging rather than silently fixing.

3. **Export scope, clarified and expanded from the original plan**: the Audit View gets its own "Export to Excel" action, not export-free as I'd first proposed. Two distinct export targets under that action: a generic tabular export of the audit view's data (always available), and a fill of the official EAD Deliverable C template (only when the user explicitly selects that option), formulas in the template untouched, data cells only. TeeKay will provide the actual template file, cell-by-cell mapping happens once it's in hand, current structural notes from the earlier session aren't sufficient for a precise fill.

4. **Framework output-selector confirmed for this phase, not deferred**: buttons/checkboxes to view/report the same underlying scope-tagged data reclassified as ISO 14064-1's six categories, GHG Protocol's scope + Scope 3 subcategory, or EAD's structure. Built alongside the source-stream entry UI in this same phase, not after.
